## 1. Задача и её сложность

Формально задача звучит просто: перед пакетной загрузкой в аналитическое хранилище определить, к какому классу конфиденциальности относятся данные. Сложность — в двух условиях из задания:

1. **Структуры на входе меняются.** Excel-файлы «Медикаменте» ведутся вручную: сегодня столбец называется `Телефон`, завтра `тел.`, послезавтра кто-то добавит колонку `Примечание`, в которую врач начнёт писать диагноз. Схема нестабильна по определению.
2. **Данные не размечены.** Никто не проставлял классы конфиденциальности — их не существует как понятия (проблема Р-32 из [Task1](../Task1)).

Из этого следует главное проектное решение: **классификация должна быть непрерывным процессом, а не разовой миграционной задачей.** Нельзя один раз разметить схему и успокоиться — при следующей выгрузке структура будет другой.

Второе решение вытекает из цены ошибки. Ошибиться можно в две стороны:

| Ошибка | Последствие | Цена |
|---|---|---|
| **Ложноотрицательная**: конфиденциальное поле распознано как публичное | ПДн попадают в открытую витрину, отдаются партнёру, уходят в обучающую выборку | **Утечка врачебной тайны** |
| **Ложноположительная**: публичное поле распознано как C3 | Поле избыточно маскируется, аналитик не видит нужных данных, стюард тратит время | Неудобство и лишняя работа |

Цена этих ошибок несопоставима, поэтому вся система намеренно смещена в сторону ложноположительных: **неопределённое считается конфиденциальным**.

## 2. Устройство движка

### 2.1. Приём и обнаружение изменений структуры

Коннекторы забирают данные из БД доменов (CDC через Debezium), из legacy-файлов Excel, из баз 1С, из Kafka и из партнёрских API. Данные попадают в **зону приземления** и сразу шифруются — до всякой классификации, потому что до классификации мы обязаны считать их максимально чувствительными.

Реестр схем хранит версии структур. **Детектор изменения структуры** сравнивает пришедшую схему с последней известной и определяет тип изменения:

| Изменение | Реакция |
|---|---|
| Новый столбец | Классификация обязательна, до её завершения — карантин |
| Изменился тип столбца | Повторная классификация |
| Переименован столбец | Повторная классификация; сопоставление по профилю данных, чтобы не потерять ранее назначенный класс |
| Изменилось распределение значений в столбце | Повторная классификация: в колонку «Примечание» могли начать писать диагнозы |
| Схема не изменилась | Классификация пропускается, берётся закешированное решение |

Последняя строка важна для производительности: подавляющее большинство загрузок не меняет структуру, и переклассифицировать их каждый раз — пустая трата ресурсов.

### 2.2. Профилирование

Классифицировать по полному объёму данных дорого и не нужно. **Сэмплер** берёт репрезентативную выборку (для нашего объёма достаточно 10 000 строк или 5 % — что больше). **Нормализатор** приводит значения к сравнимому виду: убирает разделители, приводит регистр, унифицирует форматы дат. **Профилировщик** считает признаки столбца: кардинальность, долю пустых значений, длины, распространённые шаблоны, распределение символов.

Профиль — это и вход для классификаторов, и «отпечаток» столбца, по которому работает кеш решений.

### 2.3. Ансамбль классификаторов

Один метод не справляется — у каждого свои слепые зоны. Поэтому шесть классификаторов, работающих независимо:

| Классификатор | Как работает | Сильная сторона | Слабая сторона |
|---|---|---|---|
| **Правила и регулярные выражения** | Шаблон + проверка контрольной суммы: СНИЛС, ИНН, полис ОМС, серия и номер паспорта, номер телефона | Практически нулевая доля ложных срабатываний там, где есть контрольная сумма | Бесполезен для свободного текста |
| **Словари и NER** | Модель распознавания именованных сущностей (Natasha для русского) + словари фамилий, имён, адресов | Находит ФИО и адреса в неструктурированном тексте | Ошибается на редких фамилиях, путает ФИО с названиями |
| **Справочники** | Сверка со справочниками МКБ-10, номенклатуры медуслуг, реестра лекарственных средств | Точно определяет медицинский характер данных | Работает только по известным кодам |
| **По метаданным** | Имя столбца, комментарий, имя таблицы и файла | Очень дёшев, часто достаточен: столбец `diagnosis_code` не требует анализа содержимого | Легко обманывается: `Примечание`, `Поле1`, `data` |
| **ML-классификатор** | Обучен на признаках профиля; дообучается на решениях стюардов | Ловит закономерности, которые не выражаются правилом | Требует накопленной обучающей выборки |
| **LLM-ассистент** | Локальная модель в контуре компании, анализирует маскированную выборку | Разбирает сложные случаи со свободным текстом | Дорогой; вызывается только при низкой уверенности остальных |

Про LLM отдельно: модель работает **внутри периметра компании**, ей передаётся маскированная выборка, а не сырые данные, и она никогда не является единственным источником решения — только одним голосом в ансамбле. Отправлять медицинские данные во внешний API модели нельзя ни при каких условиях.

### 2.4. Каскад по стоимости

Запускать все шесть классификаторов на каждом столбце экономически бессмысленно. Работает каскад:

```
Шаг 1 (дёшево):   метаданные + регулярные выражения + справочники
                  ↓ уверенность ≥ 0.95 → решение принято, дальше не идём
Шаг 2 (средне):   словари, NER, ML-классификатор
                  ↓ уверенность ≥ 0.85 → решение принято
Шаг 3 (дорого):   LLM-ассистент на маскированной выборке
                  ↓ уверенность ≥ 0.85 → решение принято
Шаг 4 (человек):  очередь стюарду данных
                  ↓ нет ответа в срок → остаётся в карантине с классом C3
```

По моей оценке на данных «Медикаменте» шаг 1 закроет около 70 % столбцов (большинство имеет осмысленные имена или распознаваемые форматы), шаг 2 — ещё 20 %, и только около 10 % дойдёт до дорогих шагов. Именно каскад делает решение применимым при пятикратном росте объёма.

### 2.5. Принятие решения

**Агрегатор** собирает голоса классификаторов, каждый с весом и собственной оценкой уверенности. **Оценка уверенности** маршрутизирует результат: высокая — применяется автоматически, средняя — уходит стюарду, низкая — карантин.

**Разрешение конфликтов** работает по двум правилам, оба намеренно консервативные:

1. При расхождении классификаторов выигрывает **более строгий класс**. Если один считает поле C1, а другой C3 — назначается C3.
2. **Решение человека всегда перекрывает автоматическое** и сохраняется как обучающий пример.

**Стюард данных** — это владелец домена, а не сотрудник ИТ. Класс данных — вопрос бизнес-смысла: понять, что в колонке `Примечание` лежат диагнозы, может главный врач, а не разработчик.

### 2.6. Применение политик

После присвоения класса тег записывается в каталог данных, и дальше он работает автоматически: определяет, что делать с полем (пропустить, маскировать, токенизировать, обезличить), в какой слой его положить, сколько хранить, можно ли отдавать наружу. Механизм тегирования подробно описан в [Task1/03](../Task1/03-Механизм%20тегирования%20данных.md).

## 3. Слои хранилища

Ключевое проектное решение по организации хранилища: **слой определяется не источником данных и не предметной областью, а степенью обработки персональных данных.**

| Слой | Что содержит | Кто имеет доступ | Класс | Срок хранения |
|---|---|---|---|---|
| **L0 · Карантин** | Данные, класс которых не определён | Никто из людей. Только сервисные учётки конвейера | Считается C3 | 30 дней, затем эскалация DPO |
| **L1 · Raw** | Классифицировано, но не обработано — сырые значения с тегами | Только сервисные учётки. Доступ человека — по заявке, ограничен по времени, полностью журналируется | C2/C3 | По сроку исходных данных |
| **L2 · Trusted** | Псевдонимизировано: ПДн заменены токенами, качество проверено | Инженеры данных, с маскированием на лету по политике | C2 | По сроку исходных данных |
| **L3 · Anonymized** | Необратимо обезличено: k-анонимность, обобщение, подавление редких значений | Аналитики и Data Scientists — **уровень по умолчанию** | C0/C1 | Не ограничен |
| **L4 · Витрины** | Агрегаты для BI: P&L, ABC-анализ, загрузка филиалов | Руководство, аналитики | C1 | По бизнес-потребности |
| **Песочница ML** | Обучающие выборки | Data Scientists, только внутри контура | C1 | По проекту |

Правило доступа формулируется одной фразой: **чем ближе слой к сырым данным, тем уже круг доступа; по умолчанию человек работает с самым дальним слоем.** Повышение уровня — это заявка с обоснованием, ограниченная по времени и журналируемая.

### 3.1. Меры помимо слоёв

Разделение на слои — необходимое, но недостаточное условие. Дополнительно:

| Мера | Зачем |
|---|---|
| **Отдельные ключи шифрования для каждого слоя** | Компрометация ключа L3 не даёт доступа к L1 |
| **Маскирование на лету по роли** | Один и тот же запрос к L2 возвращает разный результат инженеру и аналитику |
| **Проверка k-анонимности при переходе L2 → L3** | Формальная гарантия, что обезличивание состоялось. Если группа по квази-идентификаторам меньше порога — обобщаем дальше |
| **Подавление редких диагнозов** | Пациент с редким заболеванием идентифицируется по одной строке даже в «обезличенном» наборе. Редкие коды МКБ-10 обобщаются до группы |
| **Наследование класса вниз по потоку** | Витрина, построенная из поля C3, сама получает C3, пока преобразование не помечено как обезличивающее и не прошло проверку |
| **Lineage от источника до витрины** | Позволяет исполнить запрос на удаление и оценить масштаб инцидента |
| **Запрет прямого доступа к файлам хранилища** | Обращение только через слой доступа с применением политик |
| **Аудит всех запросов к L0–L2** | Обнаружение нетипичного поведения |
| **Автоудаление по сроку хранения из тега** | Закрывает требование своевременного удаления |
| **Отдельный контур для данных сотрудников** | HR-данные не смешиваются с клиентскими даже в обезличенном виде |

## 4. Метрики эффективности классификации

### 4.1. Метрики качества

| Метрика | Формула / смысл | Целевое значение | Почему важна |
|---|---|---|---|
| **Recall по классу C3** | Доля действительно конфиденциальных полей, распознанных как конфиденциальные | **≥ 0,99** | Главная метрика. Каждый процент недобора — это поля с диагнозами, ушедшие в открытую витрину |
| **False Negative Rate по C3** | 1 − Recall(C3) | ≤ 0,01 | То же самое с другой стороны; отслеживается отдельно, потому что это метрика утечки |
| **Precision по классу C3** | Доля верных срабатываний среди помеченных как C3 | ≥ 0,85 | Низкая точность = избыточное маскирование и недовольство аналитиков |
| **F1 по каждому классу** | Баланс точности и полноты | ≥ 0,90 | Общая оценка качества модели |
| **Coverage (полнота разметки)** | Доля полей с присвоенным классом от общего числа | ≥ 0,98 | Показывает, насколько каталог отражает реальность |
| **Доля автоматической классификации** | Решено без участия человека | ≥ 0,85 | Определяет операционную стоимость: чем ниже, тем больше нужно стюардов |
| **Согласие стюарда** | Доля автоклассификаций, подтверждённых человеком без изменений | ≥ 0,90 | Косвенная оценка точности на реальном потоке; падение — сигнал деградации модели |

### 4.2. Операционные метрики

| Метрика | Целевое значение | О чём говорит |
|---|---|---|
| Время классификации набора данных (95-й процентиль) | ≤ 15 мин | Успевает ли конвейер к утреннему построению отчётов |
| Пропускная способность (полей в час) | По профилю нагрузки | Запас по производительности |
| Размер очереди в карантине | ≤ 50 полей | Растущая очередь = движок не справляется или не хватает стюардов |
| Среднее время нахождения в карантине | ≤ 3 дней | Долгий карантин = данные недоступны бизнесу |
| Частота изменения структур (schema drift rate) | — | Показывает, насколько стабильны источники; высокая частота — повод исправлять источник |
| Стоимость классификации одного поля | Снижается со временем | Экономическая эффективность каскада |
| Доля обращений к LLM-ассистенту | ≤ 10 % | Рост означает, что дешёвые классификаторы деградируют |
| Лаг конвейера (свежесть данных) | ≤ 1 час | Актуальность аналитики |

### 4.3. Как метрики помогают оптимизировать систему

Метрики здесь не для отчётности, а как вход для конкретных решений:

| Наблюдение | Диагноз | Действие |
|---|---|---|
| Recall по C3 падает ниже 0,99 | Появился новый формат данных, который не распознаётся | Разобрать пропущенные случаи, добавить правило или запись в словарь, дообучить модель |
| Precision по C3 низкий, аналитики жалуются | Правила слишком широкие | Уточнить регулярные выражения, повысить порог уверенности, добавить контрольные суммы |
| Согласие стюарда падает | Модель деградировала или изменился характер данных | Переобучить ML-классификатор на свежих решениях стюардов |
| Очередь в карантине растёт | Не хватает стюардов или слишком много спорных случаев | Снизить порог для автоклассификации в безопасную сторону; назначить стюардов в доменах |
| Доля обращений к LLM растёт | Дешёвые классификаторы перестали покрывать поток | Перенести часто встречающиеся случаи из LLM в правила — самая дешёвая оптимизация стоимости |
| Высокая частота изменения структур у источника | Источник ведётся вручную и бесконтрольно | Не бороться следствием, а исправлять источник: ввести контроль структуры на вводе |
| Время классификации растёт линейно с объёмом | Кеш решений не работает | Проверить механизм отпечатков столбцов и инкрементальную классификацию |
| Много полей класса C3 в слое L4 | Нарушено наследование классов | Проверить пометки обезличивающих преобразований в конвейере |

Отдельно про измерение Recall: чтобы его считать, нужна размеченная эталонная выборка. Её формируют стюарды на этапе внедрения (500–1000 полей, размеченных вручную), она пополняется по мере работы и служит регрессионным тестом — прогоняется при каждом изменении правил или модели. Без такой выборки все разговоры о качестве классификации остаются умозрительными.

## 5. Масштабируемость

Компания ожидает пятикратного роста объёма данных и открывает филиалы. Что заложено в архитектуру.

### 5.1. Горизонтальное масштабирование

| Компонент | Как масштабируется | Ограничение |
|---|---|---|
| Коннекторы и профилировщик | Spark-исполнители, автомасштабирование в Kubernetes | Пропускная способность источников |
| Классификаторы | Сервисы без состояния, HPA по глубине очереди | Ресурсы кластера |
| Очередь на подтверждение | Партиции Kafka по домену данных | Число стюардов |
| LLM-ассистент | Очередь с ограничением параллелизма | GPU-ресурсы — самый дорогой компонент, поэтому и стоит последним в каскаде |
| Зона приземления и слои | Объектное хранилище масштабируется линейно | Стоимость хранения |
| Витрины | Шардирование ClickHouse, партиционирование по дате и филиалу | — |
| Каталог данных | Реплики чтения | — |

### 5.2. Что не даёт нагрузке расти линейно с объёмом

Это важнее горизонтального масштабирования: правильные решения здесь дают экономию в разы, а не в проценты.

1. **Сэмплирование вместо полного сканирования.** Классификация работает с выборкой, а не со всем массивом. При росте объёма в 5 раз размер выборки практически не меняется — растёт только точность оценки.
2. **Кеш решений по отпечатку столбца.** Отпечаток = хеш имени, типа и профиля. Если столбец не изменился, решение берётся из кеша. Это отсекает основную массу повторной работы, потому что структуры меняются намного реже, чем поступают данные.
3. **Инкрементальная классификация.** Классифицируются только новые и изменённые столбцы, а не весь набор при каждой загрузке.
4. **Каскад по стоимости.** Дорогие классификаторы вызываются для меньшинства случаев. Рост объёма данных увеличивает нагрузку в основном на дешёвые шаги.
5. **Классификация на уровне столбца, а не строки.** Класс — свойство поля, а не значения. Объём работы растёт с числом столбцов (десятки-сотни), а не строк (миллионы).

Последний пункт — принципиальный. Именно поэтому пятикратный рост числа пациентов почти не влияет на нагрузку движка: столбцов от этого больше не становится.

### 5.3. План расширения по этапам

| Этап | Объём | Конфигурация | Что добавляем |
|---|---|---|---|
| Старт (1 офис, текущий объём) | Десятки ГБ | 3 узла Spark, 1 экземпляр каждого сервиса, LLM не используется | Базовые классификаторы, ручная разметка эталонной выборки |
| Рост в 2 раза | Сотни ГБ | 5–7 узлов, HPA, кеш решений | Подключение ML-классификатора на накопленных решениях стюардов |
| Рост в 5 раз, 3–5 филиалов | Единицы ТБ | Автомасштабирование, шардирование ClickHouse по филиалам, партиционирование Kafka по домену | LLM-ассистент, приоритетные очереди, изоляция данных филиалов по атрибуту |
| Дальнейший рост | Десятки ТБ | Разделение кластеров пакетной и потоковой обработки, холодное хранилище для архива | Классификация в потоковом режиме на Flink для критичных доменов |

### 5.4. Рост числа пользователей

Число пользователей движка растёт иначе, чем объём данных: стюардов нужно примерно по одному на домен (5–7 человек, совмещающих эту роль с основной), и это число не растёт с числом филиалов — домены данных остаются те же. Растёт число потребителей аналитики, но они работают со слоями L3 и L4, которые масштабируются средствами ClickHouse и BI, а не движка классификации.

Единственное, что действительно растёт вместе с филиалами, — число источников данных. Поэтому коннекторы спроектированы как конфигурация, а не как код: подключение нового филиала — это запись в конфигурации Airflow, а не разработка.
