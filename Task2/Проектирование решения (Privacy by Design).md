# Задание 2. Проектирование решения по подходу Privacy by Design

Диаграмма: [Medikamente_C4_to-be.drawio.xml](Medikamente_C4_to-be.drawio.xml) — две вкладки: **C1 Контекст** и **C2 Контейнеры**. На вкладке C2 значком 🆕 помечены блоки, которых нет в текущей архитектуре.

## 1. Логика решения

Privacy by Design — это не набор средств защиты, которые навешиваются сверху. Это требование, чтобы приватность была свойством архитектуры, а не свойством дисциплины сотрудников. Практический критерий, которым я проверял каждое решение: **можно ли нарушить приватность, не обходя архитектуру, а просто пользуясь системой как обычно**. В As-Is ответ «да» практически везде: чтобы получить чужие медкарты, достаточно открыть сетевую папку.

Отсюда четыре опорных решения целевой архитектуры.

### 1.1. Разделение доменов данных

Главная структурная проблема As-Is — ФИО, контакты, диагноз и оплаченные услуги лежат в одной строке одного файла (Р-34). Любая утечка автоматически становится утечкой врачебной тайны.

В целевой архитектуре данные разнесены по четырём доменам с отдельными базами и **отдельными ключами шифрования**:

| Домен | Что хранит | Ключ идентификации | Класс |
|---|---|---|---|
| Идентификация | ФИО, дата рождения, контакты, документы | `patient_id` ↔ `patient_token` | C2 |
| Расписание | записи на приём, врач, время | `patient_token` | C3 (факт обращения) |
| Медицинские данные | диагнозы, анамнез, результаты, назначения | `patient_token` | C3 |
| Финансы | счета, платежи, `service_code` | `patient_token` | C2 |
| Персонал | ПДн сотрудников | `employee_id` | C2 |

Медицинский домен **не знает ФИО**. Чтобы связать личность и диагноз, нужно иметь права сразу к двум доменам, и такая операция — отдельное событие в журнале аудита. Утечка одной базы перестаёт быть катастрофой: из базы медицинских данных нельзя понять, чьи это диагнозы.

Это ровно та формулировка, которая требуется в промежуточном состоянии: *«определить категории данных пациентов и разнести их по различным доменам»*.

### 1.2. Разделение аутентификации и авторизации

`IAM (Keycloak)` отвечает на вопрос «кто это» — OIDC, MFA, роли. `PDP (Open Policy Agent)` отвечает на вопрос «можно ли этому субъекту выполнить эту операцию над этими данными». Это разные вопросы, и смешивать их в одном компоненте — типичная ошибка, из-за которой правила доступа расползаются по коду сервисов.

**RBAC** задаёт базовый уровень:

| Роль | Доступ |
|---|---|
| `PATIENT` | только собственные данные |
| `RECEPTION` | расписание, договоры, контакты; медицинские данные — нет |
| `DOCTOR` | ЭМК пациентов, которым оказывает помощь |
| `CASHIER` | счета и платежи, `service_code` без медицинской формулировки |
| `ACCOUNTANT` | финансы, зарплата; клиентские медданные — нет |
| `HR` | ПДн сотрудников; клиентские данные — нет |
| `WAREHOUSE` | ТМЦ |
| `ANALYST` | по умолчанию только слой Anonymized |
| `DPO` / `SECURITY` | метаданные, теги, журналы аудита; сами данные — нет |
| `ADMIN` | администрирование инфраструктуры без доступа к содержимому данных |

**ABAC** добавляет то, что ролью не выражается. Ключевое правило:

```rego
# Доступ к медицинским данным пациента получает только тот специалист,
# который участвует в оказании ему медицинской помощи (323-ФЗ ст. 13)
allow_emr_read {
    input.subject.role == "DOCTOR"
    some appt in data.appointments[input.resource.patient_token]
    appt.doctor_id == input.subject.id
    appt.date >= time.add_date(time.now_ns(), 0, -1, 0)   # активная или недавняя запись
    data.consents[input.resource.patient_token].special_categories == true
}
```

Обратите внимание: политика проверяет не только роль и связь «врач ↔ пациент», но и **наличие действующего согласия**. Отзыв согласия автоматически закрывает доступ, без ручных действий администратора. Это и есть Privacy by Design: правовое требование выражено в исполняемом коде, а не в регламенте, который кто-то должен помнить.

Атрибуты, участвующие в правилах: специализация врача, подразделение или филиал, статус согласия, класс данных, время суток, тип устройства, признак «данные собственного филиала».

### 1.3. Приватность как свойство по умолчанию

Требование бизнеса — *«выстроить такой подход к работе с данными по умолчанию, чтобы новые интеграции не приходилось перевалидировать»*. Реализуется тремя механизмами:

1. **Неразмеченные данные считаются конфиденциальными.** Новый столбец без тега получает класс C2 и попадает в карантин. Ошибка разработчика приводит к избыточной защите, а не к утечке.
2. **Контракт API не может отдать конфиденциальное поле молча.** Линтер OpenAPI в CI блокирует сборку, если внешний эндпоинт возвращает поле класса C2 или C3 без явного исключения, утверждённого DPO.
3. **Ответ API строится от белого списка.** Сериализация DTO идёт по явно разрешённым полям, а не «всё, кроме скрытого». Добавление поля в сущность не приводит к его автоматической утечке в ответ.

Благодаря этому новая партнёрская интеграция не требует отдельной валидации на приватность: она физически не может отдать лишнее, потому что сборка не пройдёт.

### 1.4. Полная прослеживаемость

Каждое обращение к данным класса C2 и C3 порождает запись в неизменяемом журнале: субъект, роль, ресурс, `patient_token`, основание доступа (какое правило политики сработало), результат, время. Журнал защищён хеш-цепочкой и политикой ILM от изменения задним числом.

Поверх журнала работает SIEM с правилами на аномалии: массовое чтение карт, обращение к пациенту без записи на приём, доступ в нерабочее время, всплеск выгрузок, обращение к данным чужого филиала. Срабатывание — оповещение команды. Это закрывает требование финального состояния *«проводить аудит доступа к данным и отслеживать нетипичные действия пользователей»*.

## 2. Новые блоки архитектуры

### 2.1. Периметр и контроль доступа

| Блок | Технология | Зачем | Закрывает |
|---|---|---|---|
| **API Gateway + WAF** | Kong | Единственная точка входа. TLS 1.3, mTLS между сервисами, ограничение частоты, валидация схемы, квоты на партнёра. Точка применения политик (PEP) | Р-17, Р-20, Р-22 |
| **IAM** | Keycloak | OIDC, MFA, единый вход, ролевая модель, автоматический offboarding через интеграцию с кадровым контуром | Р-22, Р-24, Р-25, Р-26 |
| **PDP — движок политик** | Open Policy Agent (Rego) | ABAC. Политики версионируются в Git, покрыты тестами, применяются одинаково во всех сервисах | Р-23, Р-27 |
| **Сервис согласий** | Java, Spring Boot | Согласия на ПДн и отдельно на спец. категории, версии текста, дата, канал получения, отзыв. Проверяется до обработки | Р-01 |
| **Сервис прав субъектов** | Java, Spring Boot | Приём и исполнение запросов: доступ к своим данным, уточнение, удаление, прекращение обработки. Оркестрирует удаление во всех доменах, озере и бэкапах | Р-02, Р-03 |
| **Сервис псевдонимизации** | Java + Vault Transit | Выдача `patient_token` и `order_id`, обратное сопоставление под отдельными правами и с полным аудитом | Р-34 |

### 2.2. Защита, аудит и реагирование

| Блок | Технология | Зачем | Закрывает |
|---|---|---|---|
| **Vault + KMS / HSM** | HashiCorp Vault | Ключи по доменам, ротация, динамические учётные данные к БД. Паролей в конфигурации не остаётся | Р-40 |
| **Сервис аудита** | Java + Elasticsearch | Неизменяемый журнал доступа к ПДн с хеш-цепочкой | Р-28, Р-30 |
| **SIEM и алертинг** | Wazuh / Elastic Security + Alertmanager | Корреляция событий, правила на аномалии, оповещение команды | Р-29 |
| **DLP** | Агенты на АРМ + почтовый шлюз | Контроль почты, съёмных носителей, печати; блокировка выгрузки данных класса C3 | Р-21 |
| **Каталог данных** | OpenMetadata | Теги классов, владельцы, lineage, политики маскирования. Единый источник правды для остальных механизмов | Р-31, Р-32, Р-33 |

### 2.3. Доменные сервисы

Десять сервисов на Java и Spring Boot — стек, которым команда уже владеет. Границы сервисов совпадают с границами доменов данных, а не с организационной структурой: это важно, потому что именно граница домена определяет границу шифрования, политики доступа и радиус поражения при утечке.

`Notification Service` заслуживает отдельного упоминания: он умышленно не имеет доступа к медицинскому домену. Он получает событие «пациенту `token` напомнить о визите на такое-то время» и не знает ни ФИО, ни специализации врача. Подстановка имени происходит в момент отправки через обращение к домену идентификации. Так утечка на стороне оператора SMS не раскрывает медицинских сведений.

## 3. Аналитический слой с учётом Privacy by Design

Это второй явный пункт задания. Требование бизнеса — создать озеро данных для BI, ML и LLM. Требование приватности — чтобы это не превратилось в тиражирование ПДн по новым площадкам, как сейчас происходит с ноутбуком аналитика.

### 3.1. Многослойная модель

| Слой | Содержимое | Кто имеет доступ | Класс |
|---|---|---|---|
| **Raw (карантин)** | Сырые данные «как пришли», ещё не классифицированные | Только сервисные учётные записи конвейера. Людям — нет | C2/C3 |
| **Trusted** | Классифицировано, ПДн заменены токенами, качество проверено | Инженеры данных по заявке, с маскированием на лету | C2 |
| **Anonymized** | Необратимое обезличивание: k-анонимность, обобщение возраста в интервалы, укрупнение адреса до района | `ANALYST` по умолчанию | C0/C1 |
| **Витрины** | Агрегаты для BI: P&L, ABC-анализ, загрузка филиалов | Руководство, аналитики | C1 |
| **Песочница ML** | Обучающие выборки из слоя Anonymized | Data Scientist, в контуре компании | C1 |

Логика в одном предложении: **чем ближе слой к сырым данным, тем уже круг доступа, и по умолчанию аналитик работает с самым дальним слоем.** Повышение уровня доступа — это заявка с обоснованием, ограниченная по времени и полностью журналируемая.

### 3.2. Как данные попадают в озеро

Ручные выгрузки Excel заменяются на CDC: `Debezium` читает журнал транзакций PostgreSQL и публикует изменения в Kafka. Это убирает целый класс проблем — аналитику больше не нужно ходить к источникам, а значит, не нужен и доступ к ним.

Перед попаданием в слой Trusted данные проходят **движок классификации** (детально спроектирован в [Task6](../Task6)). Он определяет класс каждого поля, в том числе для структур, которые изменились или пришли впервые. Неклассифицированные данные остаются в карантине.

### 3.3. Почему обезличивание, а не только маскирование

Корректно обезличенные данные перестают быть персональными и выходят из-под действия 152-ФЗ. Это не юридическая тонкость, а практическая выгода: со слоем Anonymized можно работать свободно, обучать модели, отдавать подрядчикам, хранить дольше. Поэтому в конвейер встроена **проверка k-анонимности**: если группа по квази-идентификаторам оказывается меньше порога, поля обобщаются дальше или строка исключается.

Отдельный риск, который я закладываю сразу: медицинские данные легко деобезличиваются из-за редких диагнозов. Пациент с редким заболеванием в небольшом городе идентифицируется по одной строке. Поэтому редкие коды МКБ-10 обобщаются до группы, а для особо чувствительных категорий применяется подавление значений.

### 3.4. Ограничение для ML и LLM

Обучение моделей допускается только на слое Anonymized и только в песочнице внутри контура компании. Причина — модель, обученная на сырых данных, сама становится носителем ПДн: из неё можно извлечь обучающие примеры. Для LLM дополнительно: запрет на передачу данных во внешние API моделей, использование только моделей, развёрнутых внутри периметра.

## 4. Как архитектура закрывает нефункциональные требования

| НФТ | Решение |
|---|---|
| **Безопасность и конфиденциальность** | Разделение доменов и ключей, шифрование at rest и in transit, RBAC + ABAC, аудит, DLP, SIEM. Своевременное удаление — через сроки хранения в тегах и сервис прав субъектов; прекращение обработки по запросу клиента исполняется автоматически во всех доменах |
| **Масштабируемость** | Сервисы без состояния в Kubernetes с горизонтальным автомасштабированием; Kafka как буфер между доменами; ClickHouse шардируется; филиал добавляется как атрибут, а не как новая инсталляция. Пятикратный рост объёма данных закрывается добавлением реплик и шардов, а не переписыванием |
| **Сопровождаемость** | Границы сервисов совпадают с границами доменов; политики доступа в Git и покрыты тестами; изменение правила доступа — правка политики, а не релиз десяти сервисов; стек знаком команде |
| **Конфигурируемость** | Правила доступа, классы данных, сроки хранения, политики маскирования — это конфигурация (политики Rego, теги в каталоге), а не код. Новый класс данных или новое правило вводятся без доработки сервисов |

## 5. Что попадает в MVP через два месяца

Промежуточное состояние из задания: пациент записывается через портал, ресепшен видит запись и напоминает о визите. С точки зрения приватности в MVP обязательно должно войти:

| Входит в MVP | Почему нельзя отложить |
|---|---|
| Разделение доменов «Идентификация» и «Расписание» | Позже разделять придётся с миграцией данных — дороже в разы |
| `patient_token` вместо ФИО в нецентральных доменах | Та же причина: это решение о модели данных, не о защите поверх |
| IAM с MFA и базовый RBAC | Без этого нельзя запускать внешний портал в принципе |
| Сервис согласий | Без согласия нет законного основания собирать данные через портал |
| Сервис аудита | Иначе не будет доказательной базы по инцидентам с первого дня |
| TLS 1.3, шифрование БД, Vault | Базовая гигиена, дешевле включить сразу |
| Проверка контрактов API в CI | Дешевле встроить в пустой пайплайн, чем в зрелый |

Можно отложить на последующие итерации: полноценный ABAC со сложными атрибутами (в MVP достаточно RBAC + правило «свои записи»), DLP, SIEM с обучаемыми правилами, слой Anonymized и ML-песочницу, мобильное приложение и голосового робота.

Принцип разделения простой: **в MVP входит всё, что определяет модель данных и модель доступа, и откладывается то, что можно добавить сверху без миграции.**
