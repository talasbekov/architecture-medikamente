# Задание 3. Оценка Data Encryption at Rest and In Transit

## 1. Как я классифицирую данные

Шифровать всё подряд одинаково — плохая стратегия: это дорого, замедляет систему и, что важнее, создаёт ложное ощущение защищённости. Шифрование диска не спасёт от сотрудника, который легально открыл медкарту и переслал её себе на почту. Поэтому классификация идёт по четырём осям, и уже их пересечение определяет набор мер.

**Ось 1 — чувствительность.** Шкала C0…C4 из [Task1](../Task1/02-Реестр%20данных%20и%20способы%20защиты.md): публичные, внутренние, ПДн, строго конфиденциальные (медицинские, врачебная тайна), секреты.

**Ось 2 — состояние данных.**

| Состояние | Что это | Основная угроза |
|---|---|---|
| **At rest** | В БД, файлах, объектном хранилище, бэкапах, на носителях | Физический доступ к носителю, кража бэкапа, копирование файла базы |
| **In transit** | Между сервисами, с клиентом, с партнёрами, между филиалами | Перехват в сети, MITM, ошибка маршрутизации, отправка не тому адресату |
| **In use** | В памяти процесса, на экране, в логах, в отчётах, в тестовых средах | Легитимный пользователь с избыточными правами, утечка через логи, копия продуктива в тесте |

Про третье состояние обычно забывают, а для «Медикаменте» именно оно самое актуальное: главный сценарий утечки — не хакер, а сотрудник с широким доступом.

**Ось 3 — профиль риска.** Оцениваю по двум параметрам:

| Данные | Вероятность утечки (As-Is) | Тяжесть последствий | Профиль |
|---|---|---|---|
| Медкарты, диагнозы, анализы | Высокая — доступ у всех, аудита нет | Критическая — врачебная тайна, СМИ | **Критический** |
| Факт обращения (журнал записи) | Высокая | Высокая — тоже врачебная тайна | **Критический** |
| Ключи, пароли, таблица псевдонимов | Средняя | Критическая — обнуляет все меры | **Критический** |
| Паспорт, СНИЛС, полис | Высокая | Высокая — мошенничество, штрафы | **Высокий** |
| ПДн сотрудников, зарплата | Средняя | Высокая | **Высокий** |
| Платежи и перечень услуг | Средняя | Средняя — косвенно раскрывает диагноз | **Средний** |
| Закупки, ТМЦ, P&L | Низкая | Средняя — коммерческий ущерб | **Средний** |
| Прайс, расписание | — | — | **Низкий** |

**Ось 4 — регуляторные ограничения.** 152-ФЗ, ст. 13 № 323-ФЗ (врачебная тайна), ПП РФ № 1119 (уровень защищённости — для «Медикаменте» это УЗ-1/УЗ-2), приказ ФСТЭК № 21, приказ ФСБ № 378, № 242-ФЗ (локализация), № 63-ФЗ (ЭП). Это определяет, где обязательны **сертифицированные** средства, а где достаточно свободных.

| Фото и биометрия (перспектива) | C3 | At rest | Биометрия по 152-ФЗ ст. 11 требует письменного согласия и особого режима | Шифрование, отдельное согласие, отдельный ключ, ограниченный срок хранения |
| IP, идентификаторы устройств, push-токены | C2 | At rest | Тоже ПДн; позволяют отслеживать поведение пациента | Хеширование, ограниченный срок хранения, исключение из аналитических выгрузок |

## 3. Data at Rest — как это устроено технически

Три уровня, каждый закрывает свой класс угроз. Ошибка — считать, что достаточно одного.

| Уровень | Что защищает | От чего | Чего НЕ защищает |
|---|---|---|---|
| **Диск / том** (LUKS, BitLocker) | Физический носитель | Кража сервера или диска, некорректная утилизация | Не защищает от чтения через работающую СУБД — для приложения данные прозрачны |
| **База данных** (TDE, шифрование табличного пространства) | Файлы БД и бэкапы | Копирование файла базы, доступ к бэкапу | Не защищает от легитимного SQL-запроса |
| **Поле / столбец** (`pgcrypto` + Vault) | Конкретные значения | Администратора БД, утечку дампа, ошибку в правах | Требует управления ключами и усложняет поиск по полю |

Для «Медикаменте» применяются все три, но с разной глубиной:

- **C3 (медицинские данные)** — все три уровня + отдельный ключ домена. Администратор БД без прав в Vault видит шифротекст.
- **C2 (ПДн)** — диск + БД + шифрование поля для документов (паспорт, СНИЛС).
- **C1** — диск + БД.
- **C0** — не шифруется.

Важное решение: **ключ медицинского домена не выдаётся администратору инфраструктуры**. Это разделение обязанностей, которое закрывает главную дыру любой самодельной защиты — «админ видит всё».

## 4. Data in Transit — как это устроено технически

| Канал | Мера | Обоснование |
|---|---|---|
| Пациент ↔ портал / мобильное приложение | TLS 1.3, HSTS, certificate pinning в МП | Открытый интернет, недоверенные сети |
| Сотрудник ↔ АРМ | TLS 1.3 + MFA | Устраняет доступ по факту нахождения в офисной сети |
| Сервис ↔ сервис | mTLS через service mesh (Istio) | Модель Zero Trust: сеть внутри периметра тоже недоверенная |
| Сервис ↔ БД | TLS + проверка сертификата, динамические учётные данные Vault | Убирает пароли из конфигурации |
| Система ↔ внешняя лаборатория | mTLS + OAuth 2.0 client credentials + квоты + подпись запроса | Третье лицо, наружу уходит только `order_id` |
| Система ↔ банк, ОФД, ФНС, СФР | **ГОСТ TLS** (КриптоПро NGate / ViPNet), квалифицированная ЭП | Требование регуляторов, приказ ФСБ № 378 |
| Между филиалами | ГОСТ-VPN (ViPNet Coordinator / С-Терра) | Каналы связи между площадками — незащищённые по определению |
| АРМ ↔ ККМ | Выделенный VLAN + TLS-туннель, аутентификация на уровне приложения | Закрывает Р-18: сейчас OLE по TCP/IP без всякой защиты |
| Внутренние службы (AD, файловый доступ) | LDAPS, SMB signing, запрет SMBv1 и NTLM | Закрывает Р-20 |
| Kafka | TLS + SASL, ACL по топикам | Событийная шина видит поток изменений всех доменов |

Отдельная мера, которая по эффекту важнее любого шифрования канала: **e-mail исключается из потоков с медицинскими данными**. Заключения и результаты публикуются в личном кабинете. Шифровать почту сложно и ненадёжно (ошибка адресата не лечится шифрованием), а убрать её из потока — просто.

## 5. Data in Use — то, что чаще всего забывают

| Угроза | Мера |
|---|---|
| Легитимный пользователь с избыточными правами | ABAC-правило «только участник оказания помощи»; наименьшие привилегии |
| ПДн в логах и в сообщениях об ошибках | Статический анализ в CI на поля с тегом C2/C3; маскирующий сериализатор логов |
| ПДн в трассировках и метриках | Запрет `patient_id` в атрибутах трассировки, только `patient_token` |
| Копия продуктива в тестовой среде | Синтетические или обезличенные данные; запрет восстановления боевого дампа в тест — проверяется автоматически |
| Данные на экране, съёмка экрана | Маскирование по умолчанию, раскрытие по действию (с записью в аудит); автоблокировка АРМ |
| Выгрузка в Excel и печать | DLP; водяные знаки с идентификатором сотрудника в выгружаемых отчётах |
| Экспорт через буфер обмена и съёмные носители | DLP-агент, блокировка USB-накопителей на АРМ с доступом к C3 |

## 6. Автоматизированный контроль

Меры без контроля деградируют за несколько месяцев. Что контролируется автоматически:

| Что контролируем | Как | Реакция |
|---|---|---|
| Появление неклассифицированных данных | Движок классификации + каталог данных | Данные остаются в карантине, задача владельцу домена |
| Незашифрованное хранилище | Периодический аудит конфигураций (Trivy, кастомные проверки) | Алерт ИБ, блокировка выката |
| Просроченный сертификат TLS | Мониторинг сроков в Victoria Metrics | Алерт за 30 дней |
| Отсутствие ротации ключа | Политики Vault | Автоматическая ротация, алерт при сбое |
| Поле C2/C3 во внешнем контракте API | Линтер OpenAPI в CI | **Блокировка сборки** |
| Новый столбец без тега | Проверка миграций в CI | **Блокировка сборки** |
| ПДн в логах | Статический анализ в CI | **Блокировка сборки** |
| Секрет в коде | gitleaks в CI | **Блокировка сборки** |
| Нарушение правил доступа | Автотесты политик OPA | **Блокировка сборки** |
| Аномальный доступ к данным | SIEM: массовое чтение, ночной доступ, доступ к «чужому» пациенту | Алерт команде, при критичных правилах — автоблокировка учётной записи |
| Аномальный объём выгрузки | DLP + метрики | Блокировка операции, алерт |
| Просроченные данные | Задание по срокам хранения из тегов | Автоудаление, отчёт DPO |
| Уязвимости в образах и зависимостях | Trivy, OWASP Dependency-Check в CI | Блокировка при критичных |

## 7. Реестр средств защиты

Стек двухслойный, и это сознательное решение. Для ИСПДн уровня защищённости 1–2 приказ ФСТЭК № 21 и приказ ФСБ № 378 требуют **сертифицированных** средств на уровне инфраструктуры и криптографии. При этом прикладной уровень (авторизация, токенизация, каталог данных) сертификации не требует, и там разумнее взять свободные решения, которые команда уже знает.

### 7.1. Программные средства — сертифицированный контур

| Назначение | Средство | Комментарий |
|---|---|---|

### 7.4. Управление ключами

Отдельно, потому что это самая частая точка отказа всей схемы шифрования.

| Уровень | Что | Где хранится | Ротация |
|---|---|---|---|
| Мастер-ключ | Корень доверия | HSM, разделение секрета между 3 держателями | Раз в 3 года, по регламенту |
| Ключи доменов | Отдельно для медицинского, идентификационного, HR, финансового | Vault Transit, зашифрованы мастер-ключом | Раз в год, с перешифрованием |
| Ключи данных | Для конкретных объектов и файлов | Генерируются, зашифрованы ключом домена | При каждой записи |
| Ключи ЭП | Квалифицированные сертификаты | Аппаратный носитель | По сроку сертификата |
| Ключи бэкапов | Отдельно от продуктивных | Vault + офлайн-копия в сейфе | Раз в год |

Правила: ключ медицинского домена недоступен администратору инфраструктуры; ни один ключ не хранится рядом с зашифрованными им данными; процедура восстановления ключей проверяется на учениях не реже раза в год.

## 8. Порядок внедрения

Расставляю по соотношению «эффект / стоимость», а не по формальной полноте.

| Очередь | Меры | Почему здесь |
|---|---|---|
| **1. Немедленно (1–2 мес.)** | Шифрование дисков серверов и бэкапов; отключение SMBv1 и NTLM, включение LDAPS; централизованные логи и журнал доступа к общему диску; наведение порядка в правах на файловом диске; MFA для администраторов; запрет пересылки медданных по e-mail | Дёшево, не требует миграции, снижает самые вероятные сценарии утечки уже сейчас |
| **2. Вместе с MVP (2–4 мес.)** | TLS 1.3 и mTLS; Vault; шифрование полей C3; разделение доменов и ключей; Keycloak с MFA и RBAC; сервис аудита; проверки в CI | Это решения о модели данных — позже переделывать дорого |
| **3. Развитие (4–9 мес.)** | Полноценный ABAC; сегментация сети и VLAN для ККМ; DLP; SIEM с правилами на аномалии; каталог данных и теги; сроки хранения и автоудаление; 1С в клиент-серверном режиме | Требуют настройки и обкатки, но не блокируют запуск |
| **4. Регуляторный контур (6–12 мес.)** | Сертифицированные СЗИ, ГОСТ TLS, HSM, доверенная загрузка, аттестация ИСПДн; ГОСТ-VPN между филиалами | Длинные закупки и аттестация; запускать параллельно, но не блокировать ими продукт |

Модель угроз и определение уровня защищённости ИСПДн нужно сделать в первой очереди — от них зависит состав четвёртой, а значит, и бюджет.
