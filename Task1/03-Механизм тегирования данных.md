# Задание 1, часть 3. Механизм тегирования данных

Тегирование — это то, что превращает классификацию из документа в работающий механизм. Пока класс данных существует только в таблице в Confluence, он не влияет ни на что. Как только класс становится тегом, который живёт рядом с данными и читается кодом, на него можно повесить и маскирование, и проверку в CI, и правило доступа, и срок хранения.

Именно тегирование закрывает требование из финального состояния: *«в системе есть возможность помечать тегами данные, которые необходимо защитить; релиз проверяется в автоматическом режиме на работу с тегированными данными»*.

---

## 1. Модель тега

Тег — не одна метка, а небольшой набор атрибутов. Одного «уровня конфиденциальности» недостаточно: чтобы автоматически применить политику, системе нужно знать ещё и правовое основание, и срок хранения, и способ маскирования.

```yaml
# Пример тега на поле diagnosis_code таблицы medical.encounter
data_class:      C3                    # C0 | C1 | C2 | C3 | C4
data_category:   MED_SPECIAL           # PII | MED_SPECIAL | FIN | HR | SEC | PUBLIC
legal_basis:     consent_special       # согласие по ст. 10 152-ФЗ
medical_secrecy: true                  # ст. 13 323-ФЗ
retention:       P25Y                  # срок хранения (медкарта — 25 лет)
residency:       RU                    # 242-ФЗ, локализация
masking_policy:  hide                  # none | partial | hash | tokenize | hide
owner:           domain-medical        # владелец данных
subject_type:    patient               # patient | employee | partner
pii_direct:      false                 # прямой идентификатор?
quasi_identifier: true                 # участвует в риске деобезличивания?
```

Два атрибута заслуживают отдельного пояснения:

- `quasi_identifier` нужен для аналитики. Дата рождения, район проживания, пол и дата приёма по отдельности не идентифицируют человека, но в комбинации — идентифицируют. Именно по этому флагу движок обезличивания понимает, какие поля нужно обобщать для достижения k-анонимности.
- `medical_secrecy` вынесен отдельно от `data_class`, потому что режим врачебной тайны — это не про уровень чувствительности, а про то, кому вообще законно раскрывать данные (только лицам, участвующим в оказании помощи). Это разные правила, и их надо проверять независимо.

---

## 2. Где живут теги

Тег бесполезен, если он существует в одном месте. Он должен сопровождать данные по всему пути — от схемы БД до контракта API и витрины в хранилище.

| Слой | Как хранится тег | Инструмент |
|---|---|---|
| Схема БД | `COMMENT ON COLUMN` с JSON-нагрузкой + отдельная таблица `data_catalog.column_tags` | PostgreSQL |
| Аналитическое хранилище | `COMMENT` на столбцах, теги на таблицах | ClickHouse |
| Объектное хранилище | Object tagging на объектах и бакетах | MinIO / S3 |
| Событийная шина | Аннотации в схеме Avro/Protobuf, регистрируемой в реестре схем | Schema Registry |
| Контракт API | Расширение `x-data-class` в OpenAPI/GraphQL-схеме | OpenAPI 3 |
| Код | Аннотации над DTO и сущностями | Java: `@Sensitive(clazz = C3, category = MED_SPECIAL)` |
| Инфраструктура | Метки на namespace и на PVC | Kubernetes labels |
| Каталог данных | Централизованный реестр + глоссарий + lineage | OpenMetadata (или DataHub / Apache Atlas) |

Единый источник правды — **каталог данных**. Всё остальное — проекции: каталог является тем местом, где тег заводится и меняется, а в схемы, контракты и код он растекается автоматически.

Пример аннотации в коде:

```java
public record PatientEncounterDto(
        @Sensitive(clazz = C2, category = PII, masking = PARTIAL)
        String patientToken,

        @Sensitive(clazz = C3, category = MED_SPECIAL, medicalSecrecy = true, masking = HIDE)
        String diagnosisCode,

        @Sensitive(clazz = C1, category = PUBLIC)
        LocalDateTime visitedAt
) {}
```

Пример в контракте OpenAPI:

```yaml
components:
  schemas:
    LabOrderResponse:
      properties:
        orderId:
          type: string
          x-data-class: C1          # псевдоним, наружу отдавать можно
        patientName:
          type: string
          x-data-class: C2          # партнёрскому контракту такое поле запрещено
        diagnosisCode:
          type: string
          x-data-class: C3
```

## 3. Как теги появляются

Ручная разметка не масштабируется и всегда отстаёт от изменений схемы. Поэтому три источника, в порядке приоритета:

1. **Автоматическое обнаружение.** Движок классификации (см. [Task6](../Task6)) профилирует данные и предлагает класс: по имени столбца, по регулярным выражениям и контрольным суммам (СНИЛС, ИНН, полис ОМС, серия и номер паспорта), по словарям и NER для ФИО и адресов, по справочнику МКБ-10 для диагнозов.
2. **Подтверждение владельцем данных (data steward).** Предложение с высокой уверенностью применяется автоматически, со средней — уходит в очередь на подтверждение человеку. Класс, назначенный человеком, всегда перекрывает автоматический.
3. **Разметка при проектировании.** Для новых сервисов тег ставится разработчиком в аннотации сразу — это часть определения готовности задачи (Definition of Done).

Правило разрешения конфликтов простое и намеренно консервативное: **при расхождении источников выигрывает более строгий класс**, а неразмеченные данные считаются C2 и попадают в карантин до тех пор, пока их не классифицируют. Так система ошибается в сторону избыточной защиты, а не утечки.

---

## 4. Что теги включают автоматически

Ради этого всё и делается — тег не декларация, а вход для механизмов:

| Тег | Что происходит автоматически |
|---|---|
| `data_class: C3` | Шифрование поля отдельным ключом медицинского домена; запись в журнал аудита на каждое чтение; запрет экспорта через DLP; запрет попадания в слой Anonymized без обезличивания |
| `medical_secrecy: true` | Включается правило ABAC «только участник оказания помощи»; доступ вне этого правила порождает алерт SIEM |
| `masking_policy: partial` | Маскирование при отображении для ролей без полного доступа |
| `quasi_identifier: true` | Поле обобщается при построении обезличенного слоя; проверяется k-анонимность |
| `retention: P25Y` | Задание автоматического удаления по истечении срока; учёт при запросе на отзыв согласия |
| `residency: RU` | Запрет размещения в зарубежных регионах и передачи за пределы РФ |
| `data_class: C2/C3` в контракте API | Линтер контрактов в CI блокирует сборку, если поле отдаётся во внешний API без явного разрешения |

---

## 5. Автоматический контроль в CI/CD

Это то самое «релиз проверяется в автоматическом режиме на работу с тегированными данными». Четыре проверки в пайплайне:

1. **Линтер контрактов.** Разбирает OpenAPI/GraphQL и падает, если внешний эндпоинт отдаёт поле класса C2 или C3 без явного исключения, утверждённого DPO. Закрывает требование «API-контракты должны закрывать и скрывать категории конфиденциальных данных».
2. **Проверка миграций БД.** Новый столбец без тега — сборка не проходит. Это гарантирует, что каталог не отстаёт от схемы.
3. **Проверка логирования.** Статический анализ на попадание полей с тегом C2/C3 в логи и в сообщения об ошибках. Утечка через логи — один из самых частых способов «случайно» опубликовать ПДн.
4. **Тесты авторизации как контракт.** Автотест на каждое правило ABAC: врач не может прочитать карту пациента, к которому не записан; пациент не может получить данные другого пациента. Это прямо закрывает требование «один пациент не должен иметь возможность увидеть данные другого пациента» и делает его регрессионно проверяемым.

Благодаря пункту 1 выполняется и третье требование к интеграциям: новые партнёрские интеграции не нужно перевалидировать вручную — контракт по умолчанию не может отдать конфиденциальные категории, потому что сборка просто не пройдёт.

## 6. Data Lineage

Теги дают ответ на вопрос «что это за данные», lineage — на вопрос «откуда они здесь взялись». Для «Медикаменте» это нужно в трёх сценариях:

- **Запрос субъекта на удаление.** Чтобы удалить данные, надо знать все места, куда они дотекли: домен, озеро, витрины, бэкапы, отчёты.
- **Расследование инцидента.** Если утекла витрина, нужно за минуты понять, какие исходные поля в неё попали и каких пациентов это затрагивает.
- **Оценка отчёта перед выгрузкой наружу.** Есть ли в нём производные от полей класса C3.

Технически: OpenMetadata собирает lineage из коннекторов к PostgreSQL, ClickHouse, Kafka и из заданий Airflow; каждое преобразование в конвейере регистрирует входные и выходные датасеты. Ключевое правило — **класс данных наследуется вниз по потоку**: витрина, построенная из поля C3, сама получает класс C3 до тех пор, пока преобразование явно не помечено как обезличивающее и не прошло проверку k-анонимности.

## 7. Порядок внедрения

Тегировать всё сразу невозможно, поэтому по шагам:

| Шаг | Что делаем | Результат |
|---|---|---|
| 1 | Утвердить шкалу классов и модель тега | Общий язык у ИБ, разработки и бизнеса |
| 2 | Развернуть каталог данных, подключить коннекторы к источникам | Виден полный перечень таблиц и полей (закрывает Р-31) |
| 3 | Запустить автоклассификацию по существующим Excel и базам 1С | Черновая разметка, видно масштаб проблемы |
| 4 | Назначить владельцев доменов, подтвердить и уточнить теги | Разметка, которой можно доверять |
| 5 | Подключить теги к маскированию и политикам ABAC | Тег начинает влиять на доступ |
| 6 | Включить проверки в CI сначала в режиме предупреждения | Команда привыкает, накапливается список исключений |
| 7 | Перевести проверки CI в блокирующий режим | Регресс по приватности становится невозможным |
| 8 | Подключить сроки хранения и автоудаление | Закрывается Р-02 и запросы на удаление |

Шаги 1–4 имеет смысл выполнить до начала миграции: без каталога данных невозможно ни корректно спроектировать домены, ни проверить полноту переноса.
